技能库使用手册

技能库使用手册

适用版本：skill-doctor main 分支（统一技能中心已落地） 页面入口：左侧导航「资源库 → 技能库」（原「管理与导出」页重设计而来）

1. 这个页面是干什么的？

一句话结论：技能库是本机所有 Agent 技能的「中央仓库 + 安装台账」，解决技能散落、副本漂移、无法跨 Agent 复用这三个问题。

1.1 它解决什么问题

没有技能库时，一个 skill（本质就是一个含 SKILL.md 的目录）的生命周期是这样的：

  1. 你给 Claude Code 装了一份（.claude/skills/my-skill/）；
  2. 后来用 Codex，又手动复制一份到 .codex/skills/；
  3. 三个月后你改了 Claude Code 里那份，Codex 那份还是老版本；
  4. 项目 A 里还有一份项目级副本，内容又不一样了；
  5. 没有任何一处地方能回答：“这个 skill 到底装在哪些地方？哪份是新的？”

这就是版本漂移和副本失控。技能库的思路是：

  • 唯一真相源：每个纳管的 skill 在中心仓库只存一份实体文件（默认在 ~/.skill-doctor/skills/）；
  • 安装台账：~/.skill-doctor/center.json 记录每个 skill 被部署到了哪些 Agent、哪些范围、用什么方式（复制还是链接）、内容指纹是什么；
  • 状态巡检：每次打开页面，工具会比对「中心库版本」和「各处已安装版本」的内容指纹，告诉你哪里同步、哪里过期、哪里被人改过。

1.2 页面上你能做的三件事

动作 对应操作 一句话说明
收进来 加入中心库 / 纳管 / 收回 把散落在各处的 skill 汇入中心仓库，统一登记
发出去 部署到 Agent 把中心库里的 skill 安装到任意 Agent 的项目级或全局目录
管起来 同步 / 重新链接 / 卸载 跟踪每处安装的状态，过期了拉新版，不要了干净卸载

2. 核心概念速查表

术语 是什么 存在哪里
中心仓库 纳管 skill 的实体文件存放处，所有 Agent 共用的”母本” 默认 ~/.skill-doctor/skills/，可在页面顶部「更改」为自定义目录
中心库记录 结构化台账：每个 skill 的名称、来源、内容指纹、安装列表 ~/.skill-doctor/center.json（CLI 与 UI 共同读写，改了一边另一边能看到）
已纳管（managed） 已进入中心仓库的 skill，可查看、部署、同步、卸载 列表里带「部署到 Agent」按钮的行
待纳管（physical / 未受管） 扫描发现”存在于某个 Agent 目录里、但中心库不认识”的 skill 列表里带「纳管」按钮的行，按来源 Agent 分组展示
安装（installation） 中心库 skill 在某个具体位置的部署实例，由「平台 + 范围」定位 记录在 center.json 该 skill 的 installations 数组里
安装方式 copy（独立副本）或 link（链接回中心库，Windows 用目录联接 junction） 记录在每个 installation 上
内容指纹（treeHash） 对 skill 目录全部文件算出的哈希，用于判断两份内容是否一致 中心库版本、部署版本各存一份，比对即得状态

关于 skill 的身份：中心库内部用「名称 + 平台 + 范围」派生每个安装的唯一 ID，所以同一个 skill 可以同时装在 Claude Code 全局、Codex 某项目里，互不干扰、各自跟踪状态。

3. 待纳管 vs 已纳管：是什么、从哪来、怎么用

3.1 待纳管（未受管）

定义：扫描各 Agent 的技能目录（项目级 + 全局级）后，发现磁盘上真实存在、但 center.json 里没有登记的 skill。

它从哪来： - 你以前手动复制进某个 Agent 目录的 skill； - 其他工具安装的 skill； - 本仓库自带的 skills/skill-doctor（首次使用时它就以”待纳管”身份出现——这是正常现象，不代表出错）。

判断依据：工具按目录名匹配 + 内容指纹比对。如果一个待纳管 skill 与中心库某个已纳管 skill 同名但内容不同，会标记为「同名内容不同」的冲突状态，需要你先决策（见 §4.3）。

什么时候该纳管： - ✅ 这个 skill 你以后还想在别的 Agent 上用 → 纳管，然后就能一键部署； - ✅ 你想让它有版本跟踪（过期提醒、同步）→ 纳管； - ❌ 一次性实验、或属于某个项目专属不想共享 → 可以不管它，它只是安静地躺在列表里，不影响任何功能。

3.2 已纳管（受管）

定义：中心仓库里有实体文件、center.json 里有登记的 skill。

纳管之后你获得的能力：

能力 操作入口 说明
部署到任意 Agent 行内「部署到 Agent」 选目标平台 + 范围（项目级/全局），选复制或链接
状态跟踪 安装列表的状态徽标 已同步 / 可更新 / 已修改 / 缺失 / 冲突（见 §5）
一键同步 「同步」按钮 中心库更新后，把新版推到过期的安装处
干净卸载 「卸载」按钮 删除安装处文件并清除台账记录，不留孤儿目录
关联问题 详情抽屉「查看关联问题」 跳转到「待处理」页看这个 skill 的诊断问题

4. 三个”收进来”的操作辨析

页面上有三个长得像的词，实际是同一件事的三条入口：

4.1 加入中心库（从零添加）

  • 入口：页面顶部「加入中心库」按钮。
  • 场景：skill 还不在任何 Agent 里——可能在你硬盘的某个开发目录，也可能来自 GitHub 或 Marketplace。
  • 流程：选来源（本地目录 / 手填 SKILL.md 或目录地址）→ 读取预览 → 确认。文件被复制进中心仓库并登记。
  • 注意这里没有”链接”选项：中心仓库要的是一份独立母本，源头目录以后改了不会自动跟进来。

4.2 纳管 / 收回（从 Agent 目录收编）

  • 入口：待纳管行上的「纳管」按钮（详情抽屉里叫「收回」，同一动作）。
  • 场景：skill 已经在某个 Agent 目录里活着，你想把它收编进中心库。
  • 流程（takeOver）：把该 Agent 目录里的实体文件移动进中心仓库 → 在原位置放一个指向中心库的链接 → 在台账登记这条安装。
  • 效果：Agent 侧使用完全不受影响（链接对 Agent 是透明的），但从此这份 skill 归中心库管，你直接改 Agent 目录里的文件 = 改的就是中心库母本（因为它是链接）。

换个角度理解：「纳管」=「收回」= 把实体目录搬进仓库 + 原地留下一个替身链接。两套叫法是历史页面遗留，不必纠结区别。

4.3 同名冲突怎么处理

纳管时如果中心库里已有同名但内容不同的 skill，会弹出冲突处理，两个选项：

选项 实际做的事 适合场景
保留两份并纳管当前版本 以新名称（如 my-skill-1）把当前内容存进中心库，Agent 目录链接到这个新副本 两边都是有效演化，你都想留；之后可用详情抽屉「对比版本」看差异再合并
使用中心仓库版本 先把本地原目录备份，再用指向既有中心版本的链接替换它 中心库版本是权威，本地改动是要丢弃（或已备份）的实验

页面会展示两版的逐文件 diff（新增/删除行数），帮你决策。批量纳管时，冲突项会被自动跳过，需要逐个处理。

5. 安装状态解读（最容易迷惑的部分）

每个已纳管 skill 的「安装」列表里，每条安装都有一个状态徽标。判定逻辑就是拿三个指纹互相比对：目标目录当前内容、上次部署时的内容、中心库当前内容。

状态 判定条件（白话版） 意味着什么 该做什么
已同步 synced 三者一致；或链接且确实指向中心库 一切正常 不用管
可更新 outdated 目标 = 上次部署版，但中心库已更新 中心库的母本升级了，这处安装还是旧版 点「同步」把新版推过去
已修改 modified 目标 ≠ 上次部署版 有人在 Agent 目录里直接改过这份副本 想保留改动：先手动把改动搬回中心库源目录再「同步」；想丢弃改动：直接「同步」覆盖
缺失 missing 安装路径不存在了 目录被人手动删了，或盘符变了 点「同步/重新链接」重新装回，或「卸载」清掉这条死记录
冲突 conflict 链接被换掉/断了、中心库母本被删、目录形态不对 现场与台账对不上，工具不敢自动处理 先人工看一下现场，再决定重新链接还是卸载

一个典型时间线帮你建立直觉：

纳管 skill v1 → 部署 copy 到 Codex（状态:已同步）
→ 你在中心库目录里改出 v2（Codex 那份变成:可更新）
→ 点「同步」→ Codex 拿到 v2（回到:已同步）
→ 你又直接改了 Codex 目录里的文件（变成:已修改）
→ 点「同步」强制覆盖 → 回到:已同步（你的改动被丢弃）

注意：链接模式的安装永远显示”已同步”（它就是中心库本体），复制模式才会出现”可更新/已修改”。

6. 部署到 Agent：copy 还是 link？

点已纳管 skill 的「部署到 Agent」后，需要选：目标平台、范围（当前项目 / 全局）、安装方式、冲突处理。

6.1 两种安装方式

复制 copy 链接 link
本质 独立副本，与中心库从此无关 原地留一个指向中心库的链接（Windows 上是目录联接 junction，无需管理员权限）
中心库更新后 状态变「可更新」，需手动同步 自动生效，永远是新版
在 Agent 里直接改文件 只改副本，中心库不受影响，且触发「已修改」 改的就是中心库母本，影响所有链接它的安装
适合 想为某项目做定制化变体；担心链接兼容性 追随中心库统一更新的主力技能
Windows 注意 无特殊要求 junction 必须绝对路径，且不能跨驱动器（中心库在 C 盘就别链接到 E 盘的项目）

6.2 冲突处理

如果目标位置已经有同名 skill，部署前必须为每个冲突目标三选一：覆盖目标版本 / 保留目标版本 / 跳过此目标。工具会先预览冲突，不做静默覆盖。

7. 典型场景演练

场景 A：写了个新 skill，想同时给 Claude Code 和 Codex 用

  1. 技能库 →「加入中心库」→ 选本地开发目录 → 确认（skill 进入中心仓库）；
  2. 在列表找到它 →「部署到 Agent」→ 目标选 Claude Code · 全局 · 链接 → 确认；
  3. 再「部署到 Agent」→ Codex · 全局 · 链接 → 确认；
  4. 以后改 skill 只改中心仓库里那份，两个 Agent 自动拿到新版（都是链接模式）。

场景 B：Claude Code 里已经攒了几个 skill，想共享给 Codex

  1. 打开技能库，待纳管区按 Agent 分组看到它们；
  2. 逐个（或勾选后「批量纳管」）→ 确认。原目录变成链接，实体进中心库；
  3. 对每个 skill 点「部署到 Agent」→ Codex · 复制/链接；
  4. 完成。以后 Claude Code 里直接改 skill（等效改中心库），Codex 侧若是链接自动跟上，若是复制则提示「可更新」。

场景 C：中心库里的 skill 升级了，各处副本想统一跟进

  1. 打开技能库，看到某 skill 的安装列表里出现「可更新」徽标；
  2. 逐个点「同步」，或确认后批量处理；
  3. 状态全部回到「已同步」。

场景 D：某 skill 不想要了

  • 只想从某个 Agent 摘掉：该安装行「卸载」（删文件 + 清台账，中心库母本保留）；
  • 彻底删除：详情抽屉里删除该 skill（会从中心库移除母本；各处链接安装会随之变成「冲突/缺失」状态，需再逐个卸载）。

8. 常见疑问（FAQ）

Q1：打开页面只有一条记录、中心库显示”暂无技能”，是坏了吗？ 不是。工具不做静默迁移——你已有的 skill 若都在各 Agent 目录里且没被纳管过，中心库本来就是空的，它们会以”待纳管”身份出现。这是设计行为。

Q2：「更改」中心库位置会搬家吗？ 不会自动迁移。切换位置只影响后续纳管的 skill 存放地，原中心库内容原地不动。换位置前请自行拷贝旧目录内容。

Q3：卸载会误删我的东西吗？ 卸载只删除台账登记的那条安装路径（即部署时写入的目录/文件），不碰中心库母本，也不碰其他安装。删除重复副本这类危险操作在「资源清单」页且有输入路径确认的保护。

Q4：直接在文件管理器里改 Agent 目录下的 skill 文件行吗？ 链接模式：行，等于改中心库母本（所有链接它的安装同步生效）。复制模式：行，但会触发「已修改」状态，下次「同步」会把你的改动覆盖掉。

Q5：命令行能做同样的事吗？ 能，且与 UI 共用同一个 center.json：

skill-doctor install <来源> --target <平台>   # 安装并登记到中心库
skill-doctor uninstall <名称>                 # 卸载并移除登记
skill-doctor center show                      # 查看中心库内容（JSON）
skill-doctor center migrate                   # 旧版 catalog/deployments/registry 一次性迁移

Q6：隐私方面要注意什么？ 整个技能库纯本地运行：中心仓库、台账、部署都在本机完成，不上传任何 skill 内容。只有「Marketplace」安装需要联网拉取公开条目。

9. 一页速记

  • 中心仓库 = 母本唯一存放地（~/.skill-doctor/skills/），center.json = 台账。
  • 待纳管 = “磁盘上有、台账里没有”；已纳管 = “仓库里有、可部署可跟踪”。
  • 纳管/收回 = 搬进仓库 + 原地留链接，Agent 无感。
  • 部署 = 从仓库分发到任意平台/范围；复制独立、链接跟随。
  • 状态五态：已同步（没事）/ 可更新（中心库新了，去同步）/ 已修改（副本被改了）/ 缺失（路径没了）/ 冲突（现场对不上，人工看）。
  • 一切操作本地完成，UI 与 CLI 共享同一份台账。
