# 上下文成本与预算使用手册

[手册目录](README.zh-CN.md) · [English](context-budget.md) · [返回 README](../../README.zh-CN.md#文档) · [上一篇：重复与冲突诊断](conflicts.zh-CN.md) · [命令参考](../README.zh-CN.md)

本篇适合这些场景：Agent 启动时带入的说明越来越多；想知道应先检查哪份规则或 Skill；出现「固定上下文成本超过预算」告警；需要为项目约定可复查的成本门槛。

本篇沿着一条实际流程展开：确定扫描范围 → 理解估算 → 定位高成本资源 → 核对单个 Agent → 查看超预算证据 → 调整预算并复查 → 恢复原值。完成后，你应能区分“资源成本下降”和“只是调整了告警阈值”。

## 1. 本次使用的真实环境

- 日期：**2026-10-19**；macOS；Skill Doctor 仓库版本 **0.7.1**。
- 项目：`/Users/evilstar/GitHub/skill-doctor`。
- 范围：**当前项目与全局配置**；主线使用 **跨 Agent 总览**，中途以 **WorkBuddy** 核对单个平台。
- 模式：**标准体检**，开启上下文成本；不纳入禁用资源和插件缓存，不开启 MCP 工具发现或 AI 审计／冲突分析。
- 分词器：**OpenAI tokenizer**，本次明细标为 **gpt-4o**；原预算为 **2,000 Token**。

本次仅演示扫描、来源查看和预算调整，未修改 Skill 正文、禁用资源或删除文件。预算曾临时改为 **20,000**，完成后已恢复 **2,000** 并重新体检。所有图片均为本机实际界面截图，详情使用原始局部截图以便看清读数。

## 2. 确定检查范围，进入当前占用

启动本地界面：

```bash
npx @evilstar2025/skill-doctor ui /path/to/your-project
```

替换为实际项目目录。源码运行方式见[项目体检手册](health-check.zh-CN.md#2-启动本地界面)；本次使用 `npm run dev -- ui . --port 4173 --no-open`，打开终端打印的完整本地链接。

1. 顶部「检查范围」选择 **当前项目与全局配置**，分析模式选择 **标准体检**。
2. 点击 **跨 Agent 总览**，等扫描完成；只改范围时，点击「重新体检」。
3. 在总览中点击 **可估算固定占用** 卡片。

![图 1：跨 Agent 总览中的固定占用入口与实际检查范围](../../assets/manual/context-budget/01-scan-scope.jpg)

**本例看到什么：** 总览有 **11 项待处理问题**，固定占用卡片约 **17k**，按需加载约 **182k**。卡片使用缩写，下一步进入明细读取完整数字。

**为什么先确定范围：** 跨 Agent 总览用于全机盘点和找共同来源。它将多个平台的配置估算汇总，不能解释为某一个 Agent 的某次请求实际带入了全部内容。制定某个平台的日常预算前，还应切换该 Agent 核对。

## 3. 先读懂四项指标，再判断是否需要优化

进入后，页面位于左侧「优化建议」中的 **当前占用**，此处查看当前扫描快照，不必先执行配置优化。

![图 2：当前占用显示固定 17280、按需 182087、预算 2000 和未计入 0 项](../../assets/manual/context-budget/02-context-summary.jpg)

| 指标 | 本机读数 | 含义与用途 |
| --- | --- | --- |
| 每轮固定成本 | **17,280 Token** | 按当前平台加载规则，可估算的常驻说明、启动目录或描述等固定成本；用于与预算比较，优先寻找长期带入的内容 |
| 按需激活成本 | **182,087 Token** | 启用成本条目的激活文本估算合计，常包含 Skill 完整正文；帮助发现加载后可能很大的资源，不表示这些正文已被本轮调用 |
| 预算 | **2,000 Token，评级 F** | 本次扫描的判断阈值；用于提醒固定成本是否超过预期，不是模型上下文窗口，也不会限制 Agent 实际输入 |
| 未计入的内容 | **0 项** | 当前成本条目中标为未知或不支持估算的数量；不是遗漏内容的 Token 数，也不证明运行时内容已经全部覆盖 |

**固定与按需不要直接相加。** 激活口径中也可能包含固定文件或目录项，不是相对于固定占用的纯新增量。因此不能将 `17,280 + 182,087` 作为本次请求、每轮消耗或账单。

**“0 项未计入”的边界：** 本次未连接 MCP 获取真实工具清单，MCP 相关估算可能只来自静态配置描述；Agent 隐含指令、对话历史、用户本轮输入、工具返回和后续文件读取等，也不能由这个 0 推断为没有成本。若某条显示「—／未计入」，应先补齐证据，不能按零成本处理。

**分词器如何理解：** 本次使用本地 OpenAI 分词器对估算文本计数，不需要调用模型服务。它不是一次真实模型请求的计量；当前静态估算还会规范化空白，并依资源类型选择元数据、正文或截取范围。换用「近似估算」会按字符推算，换分词器或估算范围后应重新建立比较基线。

评级只描述固定估算与预算的比例：

| 评级 | 固定估算 ÷ 预算 |
| --- | --- |
| A | ≤ 25% |
| B | > 25%，≤ 50% |
| C | > 50%，≤ 100% |
| D | > 100%，≤ 150% |
| F | > 150% |

本例 `17,280 ÷ 2,000 = 864%`，所以是 F。它不是安全评分，也不能据此推断任务一定失败。

## 4. 从成本明细定位优先检查的资源

### 4.1 先找固定成本较高的条目

**操作：** 向下滚动到「资源成本明细」，先读平台、加载方式和右侧数值，选择与你实际使用的平台相关的条目。

![图 3：明细前部的固定规则、启动描述和目录汇总](../../assets/manual/context-budget/03-cost-leaders.jpg)

**本例可先检查：**

- `AGENTS.md`：Codex，每轮固定，**1,084 Token**。
- `Repository Guidelines`：OpenCode，每轮固定，**1,084 Token**。
- `huashu-design`：WorkBuddy，启动加载，**1,032 Token**。
- `Codex skill list`：Codex，启动加载的 **11 项汇总**，**945 Token**。

**对使用者有什么帮助：** 优先审阅会持续带入、又与当前任务关系较小的说明，通常比只看磁盘文件大小更能找到方向。同名内容出现在不同平台时，应核对使用者和来源，不能假设这些成本都会出现在同一个请求中。

明细并非完整正文大小排行榜：启动加载的 Skill 行通常展示用于选择 Skill 的描述估算；按需项则可能展示激活成本。条形是相对展示，不是预算占用百分比；判断超预算以顶部固定总量和预算为准。

### 4.2 打开高成本 Skill，区分描述和正文

**操作：** 点击 **WorkBuddy** 行中的 `huashu-design`。在详情中确认平台和范围，再向下滚动到「固定成本」「按需成本」和「来源」。

![图 4：高成本 Skill 的固定成本、按需成本和本机来源](../../assets/manual/context-budget/04-high-cost-skill-detail.jpg)

**本例看到什么：** 固定成本 **1,032 Token**，按需成本 **17,855 Token**；安装入口位于 `/Users/evilstar/.workbuddy/skills/huashu-design/SKILL.md`，当前为只读。

**如何决定检查方向：** 如果关注启动时的负担，应先审阅描述和触发范围是否过长、过宽；如果关注调用后的大段上下文，应检查正文是否把大量场景、样例和操作细节一次性带入。可以考虑缩短选择说明、让正文按任务引用补充材料，但应保留必要约束并用实际任务验证效果。

1,032 与 17,855 不是“本轮已经花掉”的两个独立数值，也不能仅凭正文较大就判断该 Skill 没有价值。应结合使用频率、任务收益和正确性要求决定是否调整。本次仅查看，没有改写该资源。

### 4.3 展开汇总行，避免重复计数

**操作：** 关闭详情，点击 `Codex skill list` 下方的 **聚合来源（11）**；来源区域可继续滚动查看路径。

![图 5：目录汇总行展开后显示真实来源，汇总仍为 945 Token](../../assets/manual/context-budget/05-aggregate-sources.jpg)

**本例看到什么：** 汇总包含本机 Codex 的多个 `SKILL.md` 入口，既有用户级目录，也有当前项目中的资源。展开只是查看成员，不会新增加载内容。

**如何解读：** 目录汇总按当前估算器的目录规则计算，成员仍保留各自明细；固定总量不会把同一组 Codex 元数据成员再逐项重复相加。因此不要手工把 945 和所有成员数值再次相加，也不要将其当成实际会话中目录 block 的精确读数。

Codex 单个平台的「当前占用」还提供本地历史会话注入证据；那是所选历史会话的目录，和本节静态配置估算用途不同。详细证据边界见 [Codex 优化指南](codex-optimization.zh-CN.md)，不与本篇跨 Agent 数值混加。

## 5. 切换实际使用的 Agent，建立有意义的预算口径

**操作：** 在顶部 Agent 栏点击 **WorkBuddy**，等待自动体检结束；保持「当前项目与全局配置」，回到当前占用顶部。

![图 6：WorkBuddy 单独估算为固定 6350、按需 58881，预算仍为 2000](../../assets/manual/context-budget/06-single-agent-cost.jpg)

**本例看到什么：** 固定估算变为 **6,350 Token**，按需估算 **58,881 Token**，预算仍为 **2,000**。

**这一步的价值：** 现在可以围绕自己实际使用的平台安排审阅和预算。数值从 17,280 变为 6,350 是扫描对象改变，不是节省了 10,930 Token；不能将两个口径用于优化前后对比。

预算可根据该 Agent 的任务需要、已接受的常驻说明量和希望保留给对话／工具结果的空间设定，并随实际任务复查。本篇接下来返回 **跨 Agent 总览**，用原有汇总口径演示预算阈值变化；**20,000 只是本次演示值，不是推荐每个项目照搬的标准**。

## 6. 定位超预算告警，读取可核对的证据

**操作：** 点击顶部「跨 Agent 总览」，等待体检完成，再进入左侧「问题」。清空搜索，类型选择 **上下文**，等级保留 **需处理**。

![图 7：上下文类型下只有一条预算告警，整体仍有 11 项待处理](../../assets/manual/context-budget/07-context-budget-issue.jpg)

**本例看到什么：** 筛选结果 **1 项**：「固定上下文成本超过预算」，摘要为 **17,280 / 2,000 Token**。左侧 11 是整体问题数，不是 11 条预算告警。

点击该问题查看详情：

![图 8：预算告警详情展示固定估算、预算和优先核对的资源](../../assets/manual/context-budget/08-budget-evidence.jpg)

**如何使用证据：** 这里的数值与图 2 一致，可先从列出的高成本资源追溯来源。受影响资源是优先核对线索，不代表只要删除其中一份就能达标，也不表示未列出的资源没有成本。

## 7. 调整预算，并确认改变的是判断阈值

### 7.1 记录原值和分词器

**操作：** 关闭问题详情，点击顶部 **扫描设置**，向下找到「成本预算」。

![图 9：原每轮预算为 2000，分词器为 OpenAI tokenizer](../../assets/manual/context-budget/09-budget-settings-original.jpg)

**本例原值：** 每轮预算 **2,000**，Tokenizer 为 **OpenAI tokenizer**。先记录这些值，便于复现与恢复。保持上下文成本开启，其他分析能力、平台和范围不变。

**什么情况下该调整预算：** 当你已经审阅常驻内容并接受其价值，原阈值不再适合该扫描范围时，可以调整门槛。若目标是降低实际输入，应调整被带入的内容或加载方式，再使用相同预算复查。

### 7.2 保存新阈值并重新体检

将「每轮预算（tokens）」改为 **20000**，保持分词器不变，然后点击 **保存并重新体检**。

![图 10：仅将预算改为 20000，准备保存并重新体检](../../assets/manual/context-budget/10-budget-settings-adjusted.jpg)

等待顶部按钮恢复为「重新体检」。这会将新预算用于下一份扫描结果；只在输入框里修改，不能证明结果已更新。该操作设置 Skill Doctor 的扫描偏好，不会修改 Agent 的模型窗口或实际 Token 限额。

### 7.3 核对告警和成本两个结果

问题页保持相同搜索、类型和等级条件，查看预算告警是否变化：

![图 11：重新体检后，上下文告警为 0，整体问题数由 11 变为 10](../../assets/manual/context-budget/11-budget-alert-cleared.jpg)

再点击左侧「优化建议」，切到 **当前占用**，读取相同口径的成本：

![图 12：预算内、评级 C，但固定与按需估算都未减少](../../assets/manual/context-budget/12-budget-only-result.jpg)

| 观察项 | 调整前 | 调整后 |
| --- | --- | --- |
| 预算 | 2,000 | 20,000 |
| 固定估算 | 17,280 | 17,280 |
| 按需激活估算 | 182,087 | 182,087 |
| 状态／评级 | 超过预算／F | 预算内／C |
| 上下文预算告警 | 1 条 | 0 条 |
| 整体待处理问题 | 11 项 | 10 项 |

**本例证明了什么：** 新预算生效，`17,280 ÷ 20,000 = 86.4%`，所以评级为 C；那条预算告警不再成立，10 条重复问题仍在。资源成本未减少，不能记录成节省了 Token、费用或提升了运行速度。

## 8. 恢复原预算，留下可复查的结果

本次是手册演示，恢复已记录的原值：重新打开「扫描设置」，把每轮预算改回 **2000**，点击 **保存并重新体检**。

![图 13：将预算恢复为原来的 2000](../../assets/manual/context-budget/13-restore-budget.jpg)

等待扫描结束，再确认当前占用：

![图 14：恢复后固定 17280、按需 182087、预算 2000，重新显示超过预算](../../assets/manual/context-budget/14-restored-result.jpg)

**本例最终状态：** 固定 **17,280**、按需 **182,087**、预算 **2,000**、评级 **F**，整体仍有 **11 项待处理**。资源内容和启用状态没有变化，恢复后的结果与演示前一致。

你实际调整资源后，应保持项目、Agent、范围、分词器和预算相同，再比较对应成本与来源。扫描记录只提供兼容口径的基线；预算不同的记录不会列入同一基线选择，不能用“换预算后少一条告警”代替资源优化验证。

## 9. 根据成本来源安排处理

| 发现的情况 | 可以先做什么 | 应怎样验证 |
| --- | --- | --- |
| 每轮固定规则较长 | 审阅重复说明、过时约束和只适用于少数任务的段落，保留必要规则 | 同范围固定估算下降；新任务仍遵守必要约束 |
| 启动描述很长、触发范围很广 | 缩短选择说明，写清职责和适用条件；细节放到调用时阅读的材料 | 启动估算变化；真实任务仍能选对 Skill |
| 固定描述不大，但正文激活成本高 | 检查是否可按任务分段引用参考资料，避免每次加载无关样例 | 实际被读内容和工具记录符合预期，不只比较文件大小 |
| MCP 工具描述可能很大 | 先核对静态估算是否有真实工具清单；再评估工具暴露范围 | 获取清单后的口径一致，必需工具仍可用 |
| 未知／不支持估算 | 查明配置、可读性和检测能力，先补证据 | 未知状态得到解释，不将「—」当作零 |
| 只是预算过于严格 | 记录接受当前内容的理由，为相应平台／范围设定合理门槛 | 确认预算已应用，并明确成本是否实际变化 |

「只读／不可控」说明当前界面没有相应直接调整能力，不代表文件永远不能维护；「可写配置；待新任务验证」也不表示宿主已经采纳修改。涉及禁用或重写时，应先检查共享使用者、预览具体改动，再在实际 Agent 的新任务中验证。本篇未执行这些变更。
