# 资源清单使用手册

[手册目录](README.zh-CN.md) · [English](resources.md) · [返回 README](../../README.zh-CN.md#文档) · [上一篇：项目体检](health-check.zh-CN.md) · [平台支持范围](../platform-support.zh-CN.md)

资源清单适合回答三个实际问题：**我要找的配置在哪里？哪些 Agent 会用它？接下来应该核对或处理什么？**

接手项目、不确定某项能力从哪里来时，可以从清单追溯原文件；准备修改 Skill 时，可以先确认是否与其他 Agent 共享；出现同名条目时，可以核对它们是否来自不同位置；找不到资源时，也可以先排除筛选条件，避免重复安装。

本篇按一条完整查找流程操作，再演示同名副本和 MCP 来源两个分支。阅读后，你应能为一个资源确认：名称与类型、使用者、项目／全局范围、来源路径、声明用途、关联问题和下一步操作。

## 1. 实操环境与图片阅读方法

图片来自 **2026-10-19** 的本机实际环境：macOS、Skill Doctor 仓库版本 **0.7.1**，项目为 `/Users/evilstar/GitHub/skill-doctor`。沿用标准体检，关闭 MCP 工具发现与两项 AI 分析；顶部扫描范围为「当前项目与全局配置」，选择「跨 Agent 总览」。

本次操作只进行扫描、筛选和查看，没有调整或删除 Agent 资源。你的数量和来源会随本机配置变化，以自己的扫描结果为准。

若本机已配置 analysis 服务，打开 Skill 详情时也可能使用该服务补充解释；这是扫描阶段 AI 审计以外的另一个入口。无需为本篇新增模型配置。

清单图保留完整界面，详情图单独截取右侧抽屉原图，便于直接阅读路径和说明；点击图片可查看原始尺寸。详情后方的模糊属于界面效果，未对图片额外打码或修改数据。

## 2. 先明确要盘点的范围

**适用场景：** 想查清当前项目能接触到的资源，包括用户目录里的全局配置，并比较多个 Agent 的安装情况。

如果还未启动界面，在终端执行：

```bash
npx @evilstar2025/skill-doctor ui /path/to/your-project
```

把项目路径替换为自己的目录。源码启动方式见[项目体检手册](health-check.zh-CN.md#2-启动本地界面)；本次实际使用 `npm run dev -- ui . --port 4173 --no-open`，并打开终端打印的完整本地链接。

在界面中：

1. 将顶部「检查目标」设为 **当前项目与全局配置**。
2. 将「分析模式」设为 **标准体检**。
3. 点击 Agent 标签栏的 **跨 Agent 总览**；切换 Agent 会发起扫描。若只是改变顶部范围，则点击「重新体检」应用新范围。
4. 等按钮恢复为「重新体检」，再读取结果。

![图 1：确认当前项目与全局配置、标准体检和跨 Agent 总览，并等待扫描完成](../../assets/manual/resources/01-scan-scope.jpg)

**从这里能确定什么：** 本次结果覆盖多个 Agent，而非只检查 Codex。本机总览有 **11 项明确问题**，其中包含同名资源安装在不同位置的提示；这是后续来源追溯的线索。

**对你有什么帮助：** 先明确扫描边界，才能判断“某个资源没出现”是否只是检查范围太窄。这里的跨 Agent 结果也不能与上一篇手册中仅选 Codex 的结果直接比较，更不能把汇总成本当作一个 Agent 每轮的实际输入量。

## 3. 进入清单，建立资源底账

**操作：** 点击左侧「资源管理 → 资源清单」。初次进入时，保留全部类型、全部平台、全部范围，以及「仅有效资产（默认）」。

![图 2：未添加清单筛选时，本机返回 69 个有效资源条目](../../assets/manual/resources/02-resource-inventory.jpg)

**本例看到：** 右上角显示 **69 个资源**。列表既有项目中的 `AGENTS.md`，也有全局 Skill；相同名称的 `data-migration-kit` 分别来自 `.codex` 与 `.workbuddy`。部分条目带「共享」标记。

**如何使用这个结果：** 这是一份后续查找和变更前核对的底账。它不是 69 个 Skill 的安装清单，也不表示这 69 项已经全部注入某次对话：清单包含不同类型、共享条目和聚合条目，例如 `Codex skill list`。定位具体文件时应继续查看来源，不能只凭名称操作。

「仅有效资产」仍会显示有待处理问题的资源；“有效”不等于“没有问题”。侧栏的 **11 项问题**也不要求与资源数一致，一个问题可能关联多个资源。

## 4. 筛出某个 Agent 使用的资源

**适用场景：** 你使用 Codex 工作，想从全机资源中先找到它相关的配置，同时保留共享关系的证据。

**操作：** 在搜索框右侧的「平台」下拉框选择 **codex**。保持顶部「跨 Agent 总览」不变。

![图 3：仅改变清单内的平台筛选，结果从 69 个缩小为 18 个](../../assets/manual/resources/03-filter-codex.jpg)

**本例看到什么：** 结果缩小为 **18 个资源**。这次没有重新扫描，只是在刚才的快照中筛出使用者包含 Codex 的条目。

**对你有什么帮助：** 当你只负责某个 Agent 时，这一步能减少无关信息；共享资源仍会保留完整的使用者列表，方便评估影响范围。后续若看到「Codex、OpenCode」，不代表筛选失效，而是该资源同时被两者识别。

区分这两个层次：

| 控件 | 改变什么 | 何时使用 |
| --- | --- | --- |
| 顶部「检查范围」与 Agent 标签 | 发起扫描时的输入边界 | 当前快照没有包含目标项目、平台或全局配置时 |
| 清单内「平台／范围／类型／状态」 | 当前快照中显示哪些条目 | 已扫描到足够数据，只想缩小查找结果时 |

清单筛选不会把原本没有扫描到的资源补进来。

## 5. 用类型与关键词定位具体资源

**适用场景：** 已知大致名称，想确认项目里是否已有这项能力，避免再安装一份。

继续在当前清单中操作：

1. 将「类型」设为 **Skill**。
2. 在搜索框输入 **skill-doctor-context-optimizer**。
3. 「范围」先保留 **全部范围**，避免提前排除项目或全局资源。

![图 4：按 Skill 类型、Codex 平台和完整资源名，定位到一条共享项目资源](../../assets/manual/resources/04-search-project-skill.jpg)

**本例看到什么：** 结果为 **1 个资源**，范围是「项目」，状态是「正常」，平台列为「Codex、OpenCode」，并带「共享 · 2 Agent」。

**可以得出的结论：** 项目里已经存在这个名字的 Skill，且扫描识别到了两个使用者。接下来应核对它的用途和来源，而不是因为列表同时出现两个 Agent 就再装一份。

搜索框还会匹配路径、描述、配置来源和触发信息，不只匹配名称。例如搜索本仓库名 `skill-doctor`，还可能命中路径里包含这个词的其他项目资源。需要缩小结果时，使用更具体的名称或路径片段；搜索不是完整文件正文搜索。

## 6. 打开详情，判断它是否适合当前任务

**操作：** 点击刚才那条资源。右侧打开详情抽屉，先阅读顶部描述和「使用这个资源的 Agent」。

![图 5：共享 Skill 详情的原始局部截图，展示用途、成本和两个使用者](../../assets/manual/resources/05-shared-skill-detail.jpg)

**本例看到什么：**

- 描述说明它用于根据当前任务整理 Skills、MCP 和 Plugins，先预览、再明确确认控制操作，并报告近似上下文节省。
- 使用者列出 **Codex** 与 **OpenCode**，两者都是项目范围。
- 页面显示「只读」，同时给出固定／按需成本和按 Agent 的估算。

**这些信息怎样帮助你：**

- 当需求是“精简当前任务的上下文”时，这段描述能帮助你判断是否找对了能力；它只是声明用途，还需要结合原文和实际任务复核。
- 修改这份共享资源前，应同时考虑两个使用者，不能只验证 Codex 的表现。
- 「只读」表示当前产品不能直接对它执行相应控制，不是在说磁盘文件没有写权限，也不代表必须卸载。
- 顶部 **344 / 2,738 tokens** 是这个共享条目的聚合估算；下方分别列出 Codex **1,556**、OpenCode **1,526**。不能把这些数字全部相加后，当作 Codex 每次请求的固定占用。

激活方式和成本属于扫描口径；看到资源被列出，不等于它的完整正文已经在某次实际会话中被调用或加载。

## 7. 核对来源，找到应该阅读的文件

**适用场景：** 找到了正确的资源，但不确定应该看或修改哪个文件，或准备向维护者反馈问题。

**操作：** 在详情抽屉内向下滚动，查看「来源」「配置来源」「安装来源」「触发词与入口」和「关联问题」。需要阅读原文时，点击来源路径旁的复制图标，在自己常用的编辑器中打开该路径。

![图 6：下滚后的来源、触发信息、关联问题与技能库入口](../../assets/manual/resources/06-source-and-triggers.jpg)

**本例证据：**

```text
来源：/Users/evilstar/GitHub/skill-doctor/.codex/skills/skill-doctor-context-optimizer/SKILL.md
配置来源：builtin:scan-sources
安装来源：.codex/skills
关联问题：没有关联问题。
```

本机该入口解析后指向仓库中的[这份 Skill 原文](../../skills/skill-doctor-context-optimizer/SKILL.md)，可直接对照其描述和完整执行要求。

**怎样用这些证据：**

| 信息 | 能帮你确认什么 | 不应据此推断什么 |
| --- | --- | --- |
| 来源路径 | 应该打开哪个本地入口核对内容 | 不能凭缩略路径或名称猜另一个文件 |
| `builtin:scan-sources` | 本条由内置扫描来源规则发现 | 不表示 Skill 是官方提供或已获安全认证 |
| 安装来源 `.codex/skills` | 从哪个配置目录发现入口 | 不等于上游仓库、作者或原始发布渠道 |
| 触发词与入口 | 描述中声明了哪些用途与触发线索 | 不是宿主已触发或执行它的运行日志 |
| 没有关联问题 | 本次结果没有关联到这个条目的问题 | 不是绝对安全或效果保证 |

详情不会直接显示完整文件正文。需要确认约束、执行步骤和权限边界时，应继续读原文件；如果路径是链接，也要核对实际目标。复制路径本身不会编辑文件。

你现在可以向维护者准确反馈“哪个项目、哪个资源、哪个入口、哪些 Agent 受影响”，而不是只提供一个可能重名的 Skill 名称。「在技能库管理」是进一步管理的入口；来源核对到这里即可完成，不需要为了查看信息立即纳管或重新部署。

## 8. 查不到资源时，先排除筛选条件

**适用场景：** 刚才还在的资源突然消失，容易误以为安装丢失或扫描失败。

### 8.1 复现空结果

关闭详情，保留当前关键词、Skill 类型和 codex 平台，把清单内「范围」改为 **全局**。

![图 7：相同关键词在全局范围筛选下没有匹配结果](../../assets/manual/resources/07-empty-global-filter.jpg)

**本例为什么是 0：** 目标条目在图 4 已明确标为「项目」。当前筛选要求它同时属于全局，因此被排除；这次没有卸载资源，也没有重新扫描。

### 8.2 恢复正确范围

把同一个「范围」下拉框改为 **项目**。

![图 8：恢复项目范围后，同一资源重新出现](../../assets/manual/resources/08-project-resource-restored.jpg)

**对你有什么帮助：** 结果恢复为 **1 个资源**，证明这次消失由筛选造成，可以避免一次不必要的重装。

实际排查时，依次放宽关键词、类型、平台、范围和状态。如果仍未找到，再检查顶部扫描边界和「扫描设置 → 扫描来源与路径」，随后重新体检。列表中的「全部状态」只能放宽当前快照的显示条件；不会补回扫描时未纳入的禁用或缓存资源。

## 9. 分支一：同名资源究竟是一份共享文件，还是多个副本？

**适用场景：** 两个 Agent 的同名能力表现不同，或升级一个副本后，另一个仍使用旧内容。

从当前清单开始，明确调整以下条件：

1. 「类型」保留 **Skill**。
2. 「平台」改回 **全部平台**。
3. 「范围」改为 **全局**。
4. 将关键词替换为 **data-migration-kit**。

![图 9：两个同名资源分别来自 Codex 与 WorkBuddy 的全局目录](../../assets/manual/resources/09-same-name-different-paths.jpg)

**本例看到什么：** 出现 **2 行**，分别来自：

```text
~/.codex/skills/data-migration-kit/SKILL.md
~/.workbuddy/skills/data-migration-kit/SKILL.md
```

这与图 4 的“一行资源、两个使用者、共享标记”不同：本次清单将它们识别为两个来源，各自有「1 项需处理」。

**对你有什么帮助：** 现在可以分别核对两处内容与版本，不必凭同名就假设它们一直同步。共享资源也不保证业务行为完全相同；独立副本是否应合并，还取决于各 Agent 是否需要不同定制。

## 10. 沿关联问题验证副本来源

### 10.1 从资源进入问题

点击图 9 中 **Codex** 那一行，在详情内向下滚动到「关联问题」。

![图 10：Codex 副本的用途、完整来源和关联的重复问题](../../assets/manual/resources/10-resource-linked-issue.jpg)

**本例看到什么：** 来源是 Codex 用户目录中的 `SKILL.md`；描述涉及数据迁移交付物，关联问题是 **发现重复资源：data-migration-kit**。

**这一步的价值：** 先确认自己正在查看哪份文件、它原本用于什么，再处理问题，避免误操作另一份同名配置。这里的「1 项需处理」是关联问题数量，不能直接解释为一条恶意指令。

### 10.2 核对问题证据

点击该关联问题，详情切换为重复问题的证据。

![图 11：重复问题明确列出副本 A、B 的完整路径](../../assets/manual/resources/11-duplicate-path-evidence.jpg)

**本例可以确认：** 问题的副本 A 指向 `.codex/skills`，副本 B 指向 `.workbuddy/skills`，与图 9 的两行来源一致。需要调查版本漂移时，可以携带这两个路径继续逐文件比较，而不是只提供“有重复”的截图。

**下一步怎样判断：** 先核对两份内容、维护来源和各 Agent 的用途，再决定分别保留、统一管理还是清理。本篇在核对证据后关闭详情，不填写删除确认，也不执行删除；界面上的“保留一份”建议不能替代这一步判断。后续比对方法可参考[命令参考中的 `diff` 与 `conflicts`](../README.zh-CN.md)。

## 11. 分支二：MCP 到底来自项目配置还是全局配置？

**适用场景：** 某个项目出现了 MCP server，你需要找出配置入口；或者界面显示正常，但实际工具仍无法使用。

### 11.1 定位项目 MCP

关闭详情，清空搜索框，将「类型」改为 **MCP**、「平台」改为 **codex**、「范围」改为 **项目**。本次仍使用顶部的跨 Agent 扫描快照。

![图 12：筛出 Codex 项目范围的 MCP，找到 ast 配置条目](../../assets/manual/resources/12-project-mcp-config.jpg)

**本例看到什么：** 列表只有 **ast**，来源缩略路径为当前项目的 `.codex/config.toml`，状态是「正常」。

**对你有什么帮助：** 这次应先检查项目配置入口，不必从所有用户级 MCP 配置中逐个翻找。若寻找的是全局 server，需要相应放宽清单范围，并确认顶部扫描已包含全局配置。

### 11.2 查看来源与证据边界

点击 **ast**，查看右侧详情。

![图 13：MCP 的实际来源路径及当前扫描能给出的信息](../../assets/manual/resources/13-mcp-source-detail.jpg)

**本例可以确认：** 配置入口为 `/Users/evilstar/GitHub/skill-doctor/.codex/config.toml`。页面显示「正常」「没有关联问题」，但本次标准体检没有进行 MCP 工具发现。

**不能据此确认：** server 当前能够启动、认证成功、工具列表可获取，或 Agent 已经实际调用它。页面中的 `46 tokens` 等数值也不能当作已经取得全部实时工具 schema 的证据。

因此，排查“工具用不了”时，可以先凭来源路径核对配置，再根据需要检查实际服务与工具发现；不要因为清单状态正常就停止排查。打开来源文件前也要确认是在检查配置，不要直接把“可控制：支持”理解为需要禁用 server。本次未点击「审阅调整」。

## 12. 把查找结果变成可行动的信息

完成主线后，本例已经得到一份可以交接给维护者的信息：

| 要确认的事 | 本例结论 | 对后续工作的帮助 |
| --- | --- | --- |
| 找到了什么 | `skill-doctor-context-optimizer`，项目 Skill | 避免按模糊名字重复安装 |
| 用来做什么 | 声明用于按任务精简上下文，先预览再确认 | 判断它是否适合当前需求 |
| 谁会受影响 | 扫描识别到 Codex、OpenCode 共享 | 修改后需要考虑两个使用者 |
| 应读哪个文件 | 图 6 的完整来源及其实际链接目标 | 防止改错另一个同名文件 |
| 本次是否有问题 | 目标 Skill 无关联问题；另一个同名案例有重复问题 | 区分继续使用、进一步审查和维护整理 |

不同情况的后续动作：

- **符合任务且来源正确：** 保留现状，按需要阅读完整 Skill 说明。
- **准备修改共享资源：** 先确认使用者与链接目标，再安排对应 Agent 的验证。
- **同名多来源：** 核对各副本内容与用途，再决定是否统一管理。
- **清单为空：** 先排除筛选和扫描范围，再考虑安装是否缺失。
- **MCP 配置存在但工具不可用：** 继续检查服务与运行时证据，不能只看资源状态。

资源清单的作用是提供可追溯的判断依据；实际调用记录、完整安全结论和运行时成本需要相应证据，不能由清单代替。
